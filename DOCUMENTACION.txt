--------------------------------------------------------------------------------
1. QUÉ HACE (RESUMEN EN UNA FRASE)
--------------------------------------------------------------------------------

LegoSearch lee fuentes RSS públicas relacionadas con LEGO, detecta menciones de
sets concretos de una lista de inversión (WATCHLIST), extrae precios del texto y
calcula si comprar a ese precio tendría beneficio al revender.

No compra, no notifica y no hace scraping de tiendas. Solo genera datos
(JSON y CSV) para que otro sistema decida.


--------------------------------------------------------------------------------
2. ESTRATEGIA "LEAN": POR QUÉ NO HAY SCRAPING
--------------------------------------------------------------------------------

Se descartó a propósito el scraping de tiendas (Amazon, El Corte Inglés,
LEGO.com) porque:
  - Están protegidas por Cloudflare y bloquean bots de forma agresiva.
  - Requieren mantenimiento constante cuando cambian las defensas.
  - El riesgo de banear la IP es alto.

En su lugar se usan feeds RSS públicos y la API oficial de Brickset.


--------------------------------------------------------------------------------
3. DÓNDE SE BUSCA — LAS 6 FUENTES RSS
--------------------------------------------------------------------------------

Cada fuente tiene un "tipo" (orienta cómo se interpreta la señal) y un
"valor_eur" (fiabilidad de 0 a 1, que pondera la puntuación final).

  #  NOMBRE                  TIPO        FIAB.  URL
  -- ----------------------- ----------- -----  --------------------------------
  1  Reddit r/legodeals      ofertas      1.00  https://www.reddit.com/r/legodeals/.rss
  2  Chollometro (LEGO)      ofertas      1.00  https://www.chollometro.com/rss/nuevos
  3  Brick Fanatics          eol          0.55  https://www.brickfanatics.com/feed/
  4  Reddit r/lego           noticias     0.40  https://www.reddit.com/r/lego/.rss
  5  Brickset News           noticias     0.35  https://brickset.com/feed
  6  The Lego Car Blog       noticias     0.20  https://thelegocarblog.com/feed/

  ORDENADO POR FIABILIDAD. Pesos revisados tras medir el rendimiento real:
  solo las fuentes de tipo "ofertas" pueden aportar descuentos reales. Los
  blogs de noticias citan PVP de lanzamiento y quedan en papel secundario
  (0.20-0.35). Brick Fanatics mantiene 0.55 por sus señales de retirada (EoL),
  que alimentan el calendario.

TIPOS:
  - "ofertas"  : agregadores/comunidades de chollos. La señal más valiosa.
  - "eol"      : fuentes que anuncian retiradas de sets (End of Life).
  - "noticias" : blogs y prensa especializada (lanzamientos, rumores).

PROBLEMA CONOCIDO DE LAS FUENTES
  En una ejecución real: 165 entradas -> 109 hablan de LEGO -> solo 5 traen
  un precio. Y de esas 5, casi todas son anuncios de lanzamiento (el precio es
  el PVP oficial), no ofertas. Es decir: los feeds son de NOTICIAS, no de
  CHOLLOS. Esta es la limitación principal del proyecto.

  Detalle por fuente (medido):
    Brickset News        40 entradas |  5 con LEGO+precio (todas PVP de lanzamiento)
    Brick Fanatics       50 entradas |  0 con precio
    The Lego Car Blog    20 entradas |  0 con precio
    Reddit r/legodeals   25 entradas |  0 con precio parseable
    Chollometro          30 entradas |  0-2 con LEGO (feed rotativo)

  NOTA SOBRE REDDIT: bloquea con HTTP 429. Se comprobó que el bloqueo no es por
  el User-Agent sino por la huella TLS de la librería `requests`. Solución
  aplicada: esos feeds se descargan con `curl`. Aun así, Reddit limita a ~1
  petición por minuto por IP, así que entre los dos subreddits se espera 62 s.
  En GitHub Actions (IPs compartidas) puede fallar igualmente.

4. LA FUENTE DE DATOS OFICIALES: API DE BRICKSET
--------------------------------------------------------------------------------

Se usa para lo que los RSS no pueden dar: datos verificados por set.

  URL base: https://brickset.com/api/v3.asmx
  Requiere: BRICKSET_API_KEY (gratuita, en brickset.com/tools/webservices)
  Sin key: todo funciona igual, pero con los precios de config.py

  DETALLE IMPORTANTE DE LA API:
    - El parámetro setNumber EXIGE el sufijo "-1" ("75192-1"). Sin él devuelve
      "success" con 0 sets: un fallo silencioso.

  QUÉ DEVUELVE (verificado):
    [OK]   PVP oficial por país  -> LEGOCom["DE"]["retailPrice"] (proxy del PVP €)
    [OK]   Fecha de retirada     -> exitDate ("2026-12-31")
    [OK]   Metadatos             -> piezas, minifigs, temática, rating
    [NO]   Precios de mercado    -> NO los publica. Ni BrickLink ni Amazon.

  Consecuencia: el PVP y la fecha de retirada son datos reales; el precio de
  REVENTA sigue siendo una estimación manual de config.py.

7. CRITERIOS DE FILTRADO — EL "FILTRO DUAL"
--------------------------------------------------------------------------------

Una entrada debe superar TODOS estos filtros para convertirse en oportunidad.

  A) CONTEXTO LEGO (obligatorio)
     El texto debe contener "lego", "brick" o "minifig".
     Evita falsos positivos como confundir el set NES (71374) con una oferta
     de videojuegos de "Nintendo Switch".

  B) CRITERIOS DE COLECCIONISTA (mínimo 1 de 3 puntos)
     - Público adulto AFOL (18+, UCS, Icons)        -> 1 punto
     - Volumen alto: >= 1.000 piezas                -> 1 punto
     - Minifiguras exclusivas                       -> 1 punto
     Con 1 punto ya pasa (antes eran 2).

  C) VIGENCIA DE LA SEÑAL
     - Entradas de tipo "ofertas": máximo 45 días de antigüedad
     - Entradas de tipo noticias/EoL: máximo 365 días

  D) PRECIO CREÍBLE Y ANTI-MSRP (regla estricta)
     El precio detectado debe cumplir DOS condiciones:
       - Ser mayor o igual al 10 % del PVP (por debajo se asume error de regex:
         cuota de sorteo, cupón, pieza suelta).
       - Ser ESTRICTAMENTE inferior al PVP con al menos un 5 % de descuento.
     Un blog que anuncia un lanzamiento cita el PVP oficial; ese precio NO es
     una oportunidad, es el precio de salida. Por debajo del 5 % de descuento
     se considera ruido de redondeo.

  D2) ENTRADAS SIN PRECIO (descartar_sin_precio = True)
     Si una entrada solo cita sets y no aporta ningún importe real con
     descuento, es una noticia (lanzamiento, rumor, EoL). Se descarta y NO
     genera "señal_vigilancia". Esto evita que la tabla se llene de sets a
     precio objetivo que parecen oportunidades sin serlo.

  E) CONFIANZA DE CRUCE (mínimo 25 sobre 100)
     Mide cuánto creemos que el texto habla DE ESE set:
       - Referencia numérica en el título        -> 95
       - Referencia numérica en el cuerpo        -> 75
       - Solo coincidencia por nombre en título  -> 70
       - Solo coincidencia por nombre            -> 50
       +10 si hay lenguaje de oferta
       +10 si aparece "oferta/chollo/deal"
       +5  si la fuente es de tipo "ofertas"

  F) UMBRALES FINANCIEROS
     - ROI neto mínimo: 25 %
     - Beneficio neto mínimo: 10 €

  G) SCORE TOTAL mínimo: 30 sobre 100

  NOTA: los umbrales de score están BAJOS a propósito. El score sirve para
  ORDENAR la tabla, no para esconder resultados.


--------------------------------------------------------------------------------
8. CÁLCULO FINANCIERO
--------------------------------------------------------------------------------

  FÓRMULAS (configurables en FINANZAS):
    gastos_plataforma = precio_venta x 10 %
    gastos_envio      = precio_venta x 5 %
    coste_total       = precio_compra + gastos_plataforma + gastos_envio
    ingresos_netos    = precio_venta - gastos_plataforma - gastos_envio
    beneficio_neto    = ingresos_netos - precio_compra
    roi_pct           = beneficio_neto / coste_total x 100

  PLAZO DE REVENTA ESTIMADO (según estado del set):
    - Retirado / EoL   ->  1 mes   (mercado escaso, giro rápido)
    - Próximo EoL      ->  6 meses
    - Activo           -> 18 meses (esperar a la retirada)

  MARGEN MENSUAL = ROI / meses de tenencia
    Permite comparar un giro rápido del 40 % con una tenencia de 18 meses al 80 %.

  AVISO IMPORTANTE: el precio de reventa NO está verificado (Brickset no lo
  publica). El campo plan_reventa.valor_verificado = false lo indica, y en la
  tabla aparece marcado con "⚠".


--------------------------------------------------------------------------------
9. PUNTUACIÓN (SCORE 0-100)
--------------------------------------------------------------------------------

  Componente            Peso   Cómo se calcula
  --------------------  -----  ---------------------------------------------
  Calidad coleccionista   30   (puntos/3) x 30
  Confianza de cruce      25   (confianza/100) x 25
  ROI                     25   ROI/150 x 25 (150 % = puntuación plena)
  Fiabilidad de fuente    10   valor_eur x 10
  Frescura                10   según días de antigüedad
  Bonus objetivo          +5   si el precio <= objetivo de compra
  --------------------  -----
  MÁXIMO                 105

  ORDENACIÓN FINAL: score + (margen_mensual x 0,5), de mayor a menor.
  Se deduplica por set: solo la mejor entrada de cada referencia.


--------------------------------------------------------------------------------
10. TIPOS DE RESULTADO
--------------------------------------------------------------------------------

  "chollo"            -> se encontró un precio real en una fuente
  "señal_vigilancia"  -> set interesante SIN oferta activa; el precio de
                         compra es el objetivo del usuario, no un precio real

  En la práctica, casi todos los resultados actuales son "señal_vigilancia".

11. FUNCIONES PRINCIPALES (main.py)
--------------------------------------------------------------------------------

  RASTREO
    rastrear_feeds()            Descarga los 6 feeds y aplica pausas por host.
    _descargar_bytes()          Elige transporte: requests o curl (Reddit).
    descargar_feed()            Descarga y parsea, con reintentos y backoff.
    construir_entradas()        Convierte el feed en objetos Entry.

  EXTRACCIÓN
    extraer_precios()           Regex multilingüe: "599,99 €", "€599.99",
                                "EUR 84.99", "84.99€", "599 euros".
                                Distingue si el precio es oferta o PVP.
    extraer_referencias()       Detecta números de set (4-6 dígitos, excluye años).
    detectar_referencias_meta() Cruza referencias y alias con la watchlist.

  EVALUACIÓN
    evaluar_coleccionista()     Puntúa 0-3 (AFOL, piezas, minifigs exclusivas).
    confianza_cruce()           Calcula 0-100 de que hable de ese set.
    elegir_precio_compra()      Decide qué precio usar como precio de compra.
    calcular_financiero()       Gastos, beneficio neto y ROI.
    calcular_score()            Score compuesto 0-100.
    evaluar_oportunidades()     Aplica el filtro dual completo.

  EXPORTACIÓN
    estimar_reventa()           Plazo y precio de venta sugerido.
    serializar_candidate()      Convierte a dict para el JSON.
    actualizar_historico()      Acumula sin duplicar.
    _ordenar_y_ranquear()       Ordena por interés y deduplica por set.
    escribir_json_atomico()     Escritura segura (nunca deja JSON a medias).
    escribir_csv()              CSV con ";" y BOM UTF-8 para Excel.
    escribir_reporte_md()       Reporte legible con tablas.

  SUELO HISTÓRICO
    calcular_suelo_historico()  Precio de compra más bajo visto por set.
    _contraste_suelo()          Compara la oferta actual con ese mínimo.

  WORKER
    modo_loop()                 Bucle continuo con SIGTERM limpio.
    _segundos_intervalo()       Resuelve el intervalo (CLI > env > 6 h).

  CALENDARIO
    construir_calendario()      (calendario.py) Sets que se retiran y cuándo.
    BricksetClient.datos()      (brickset.py) Datos oficiales de un set.

13 bis. SUELO HISTÓRICO DE PRECIOS (precio_minimo_historico)
--------------------------------------------------------------------------------

  QUÉ ES
  El precio de compra más bajo que se ha visto nunca para cada set, calculado
  sobre TODO el histórico acumulado en opportunities.json.

  POR QUÉ
  El PVP dice cuánto cuesta nuevo, pero no si una oferta es buena DE VERDAD.
  Si hoy ves el 71043 a 289,90 € y en febrero estuvo a 240 €, el ROI frente al
  PVP puede seguir siendo bueno y aun así ser una mala compra. El suelo
  histórico responde a: "¿ya se ha visto más barato?".

  CÓMO FUNCIONA
  1. Se recorre el histórico y se toma min(precios.compra) por referencia.
  2. Solo cuentan las ofertas REALES (precios.origen = "oferta_detectada").
     Los "precio_objetivo_compra" se excluyen: son metas del usuario, no
     precios que nadie haya pagado nunca, y ensuciarían el mínimo.
  3. Cada oportunidad recibe un bloque "contraste_suelo":

       "contraste_suelo": {
         "precio_actual": 289.9,
         "precio_minimo_historico": 240.0,
         "es_minimo_historico": false,
         "mejora_vs_minimo_pct": -20.79,
         "nota": "por encima del mínimo visto (240.00 €)"
       }

  4. El JSON publica además "suelos_historicos", un mapa set -> mínimo con
     fecha, fuente y URL de dónde se vio. Así el bot puede enseñar "visto a
     240 € en Chollometro el 2026-02-01".

  DÓNDE SE VE
  - JSON:      bloque contraste_suelo + suelos_historicos
  - CSV:       columnas "Mín. histórico €", "¿Nuevo mínimo?", "Mejora vs mín. %"
  - Markdown:  🏆 delante del precio cuando bate o iguala el mínimo

  NOTA SOBRE EL ALMACENAMIENTO
  Se calcula sobre el JSON histórico acumulado; no hay base de datos SQLite en
  este proyecto. Si en el futuro se añade, el cálculo es el mismo: basta con
  un SELECT min(precio) GROUP BY referencia.

13 ter. DESPLIEGUE COMO WORKER (RAILWAY / DOCKER)
--------------------------------------------------------------------------------

  VARIABLES DE ENTORNO
    BRICKSET_API_KEY          Obligatoria para PVP y fechas de retirada.
    LOOP_MODE                 1 = proceso continuo; 0/vacío = una pasada.
    SCAN_INTERVAL_MINUTES     Minutos entre escaneos (defecto 360 = 6 h).
    LEGOSEARCH_OUTPUT         Ruta del JSON (en Docker: /app/data/...).
    TZ                        Europe/Madrid (en la imagen ya viene puesto).

  PRIORIDAD DEL INTERVALO
    --interval (CLI)  >  SCAN_INTERVAL_MINUTES  >  360 min

  COMPORTAMIENTO DEL WORKER
    - Un ciclo que falla se registra y se sigue; el proceso no muere.
    - SIGTERM/SIGINT (lo que manda Railway al redesplegar) corta la espera al
      instante y sale con código 0 para no provocar reinicios en bucle.
    - Jitter de hasta 5 % en la espera, para no golpear los feeds siempre a
      la misma hora exacta.

  FICHEROS
    Dockerfile        Imagen python:3.12-slim con curl y usuario sin root.
    .dockerignore     Excluye .venv, datos locales y secretos.
    railway.json      Builder Dockerfile + startCommand + reinicio ON_FAILURE.
    .env.example      Plantilla de variables (esta SÍ se versiona).

  ARRANQUE LOCAL
    docker build -t legosearch .
    docker run --rm -e BRICKSET_API_KEY=xxx -v legosearch_data:/app/data legosearch

  EJECUCIÓN ÚNICA (cron externo, CI)
    docker run --rm legosearch python main.py --once

  IMPORTANTE: monta /app/data como volumen. Si no, cada redespliegue borra el
  histórico y se pierden los suelos acumulados.

14. LÍMITES CONOCIDOS Y TAREAS PENDIENTES
--------------------------------------------------------------------------------

  1. NO HAY FUENTE DE CHOLLOS REALES
     Los feeds son de noticias. De 165 entradas, solo ~5 traen precio y casi
     siempre es el PVP de un lanzamiento. Esta es la limitación de fondo.
     Mitigado con la regla anti-MSRP: ahora esas entradas se descartan en vez
     de entrar como oportunidad. Consecuencia esperada: muchas ejecuciones
     devuelven 0 oportunidades. Eso es correcto, no un fallo.

  2. EL PRECIO DE REVENTA NO ESTÁ VERIFICADO
     Es una estimación manual. Brickset no publica precios de mercado.
     Todo el ROI depende de ese número.
     Siguiente paso propuesto: API de BrickLink (requiere OAuth 1.0a). Estaba
     en mantenimiento cuando se intentó; sin verificar.

  3. REDDIT ES POCO FIABLE
     Límite de ~1 petición/minuto por IP. En GitHub Actions probablemente falle.

  4. CHOLLOMETRO ES ROTATIVO
     El feed de novedades trae LEGO de forma intermitente (0 a 2 menciones).

  5. COBERTURA EoL DEL 50-60 %
     No todos los sets tienen fecha de retirada publicada.

  6. CORREGIDO RECIENTEMENTE
     - 24 sets tenían PVP y estado EoL equivocados en config.py
     - El JSON publicado iba una ejecución por detrás (bug de git checkout)
     - Reddit daba 429 al 100 % de las peticiones
